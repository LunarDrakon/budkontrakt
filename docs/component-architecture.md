# Компонентна архітектура

## 1. Призначення застосунку

Застосунок розробляється для вебсайту ремонтно-будівельної компанії.

Основне призначення сайту — представити послуги компанії, надати користувачам можливість переглядати інформацію про послуги, знаходити потрібні варіанти та залишати заявки на виконання ремонтних і будівельних робіт.

У межах лабораторної роботи 3.1 функціональність застосунку було доповнено операціями створення, перегляду, редагування та видалення заявок, перевіркою введених даних, а також пошуком, фільтрацією та сортуванням списку заявок.

## 2. Основні частини інтерфейсу

Основними частинами інтерфейсу є:

- спільна шапка сайту;
- основна навігація;
- головна сторінка;
- список послуг;
- картки окремих послуг;
- сторінка деталей послуги;
- розділ заявок;
- сторінка створення заявки;
- сторінка перегляду заявки;
- сторінка редагування заявки;
- засоби пошуку, фільтрації та сортування заявок.

## 3. Компонентна ієрархія

Основна структура компонентів має такий вигляд:

```text
App
└── AppLayout
    ├── SiteHeader
    ├── MainNav
    └── Outlet
        ├── HomePage
        ├── ServicesPage
        │   └── ServiceList
        │       └── ServiceCard
        ├── ServiceDetailsPage
        └── RequestsLayout
            └── Outlet
                ├── RequestsPage
                │   ├── пошук заявок
                │   ├── фільтрація та сортування
                │   └── список результатів
                ├── RequestCreatePage
                ├── RequestDetailsPage
                └── RequestEditPage
```

Окремо для роботи із заявками використовується `RequestsContext`, який надає доступ до спільної колекції та операцій над нею.

## 4. Відповідальність компонентів

### App

Кореневий компонент React-застосунку. Містить опис маршрутів і визначає, який компонент потрібно відображати для кожної адреси.

### AppLayout

Спільна маршрутна оболонка застосунку. Містить `SiteHeader`, `MainNav` та `Outlet`, через який відображається вміст поточного маршруту.

Також у `AppLayout` розміщено `SelectedServiceProvider`, завдяки якому вибрана послуга доступна відповідним дочірнім компонентам.

### SiteHeader

Відповідає за відображення назви ремонтно-будівельної компанії та короткого опису її діяльності.

### MainNav

Містить основну навігацію сайту. Для переходів між маршрутами використовується `NavLink`.

Основні розділи навігації — головна сторінка, послуги та заявки.

### HomePage

Головна сторінка вебсайту. Містить інформацію про компанію та елементи для ознайомлення з її послугами.

### ServicesPage

Сторінка зі списком послуг компанії. Для пошуку послуг використовується параметр `search` в URL.

### ServiceList

Відповідає за відображення списку послуг. Отримує масив послуг через `props` та передає окремі записи компоненту `ServiceCard`.

### ServiceCard

Відображає інформацію про одну послугу: назву, категорію, опис, ціну та доступність. Для оформлення карток використовується React Bootstrap.

Посилання на назву послуги відкриває сторінку її деталей за адресою `/services/:serviceId`.

### ServiceDetailsPage

Відображає детальну інформацію про вибрану послугу. Ідентифікатор отримується з URL за допомогою `useParams`.

Якщо послугу з указаним ідентифікатором не знайдено, відображається відповідне повідомлення та посилання для повернення до списку послуг.

### RequestsLayout

Маршрутна оболонка розділу заявок. Містить локальну навігацію за допомогою `NavLink` та `Outlet` для відображення дочірніх сторінок.

### RequestsPage

Відповідає за відображення списку заявок клієнтів. На сторінці можна переглянути кількість заявок, перейти до створення нової заявки, відкрити деталі наявної заявки або перейти до її редагування.

У лабораторній роботі 3.1 сторінку доповнено пошуком за ім’ям замовника та описом робіт, фільтрацією за потребою в замірах і сортуванням за ім’ям замовника або площею робіт.

Для роботи з параметрами пошуку, фільтрації та сортування використовується `useSearchParams`. Вибрані параметри відображаються в URL, а список автоматично формується відповідно до встановлених умов.

Також передбачено окремі повідомлення для порожньої колекції заявок і ситуації, коли за заданими умовами пошуку результатів немає.

### RequestCreatePage

Відповідає за створення нової заявки. Користувач вводить дані замовника та інформацію про заплановані роботи.

Перед створенням заявки перевіряється правильність введених значень. Якщо дані не відповідають установленим правилам, користувач отримує повідомлення про помилки. Перехід після успішного створення виконується лише тоді, коли операція завершилася успішно.

### RequestDetailsPage

Відповідає за перегляд збереженої заявки. На сторінці відображаються її основні дані: ідентифікатор, код послуги, ім’я замовника, телефон, опис робіт, площа та інформація про потребу в замірах.

Для отримання ідентифікатора заявки використовується `useParams`. Якщо запис не знайдено, відображається повідомлення про його відсутність.

На сторінці також доступні переходи до редагування та повернення до списку заявок. Перед видаленням заявки користувач повинен підтвердити свою дію.

### RequestEditPage

Відповідає за редагування наявної заявки. Ідентифікатор запису отримується з URL за допомогою `useParams`.

Під час редагування застосовуються правила перевірки введених даних. Зміни передаються до спільної колекції заявок, а перехід до іншої сторінки виконується після успішного завершення операції.

### NotFoundPage

Відображається для невідомих маршрутів. Містить повідомлення про те, що сторінку не знайдено, та посилання для повернення на головну сторінку.

## 5. Дані

Дані про послуги зберігаються окремо у файлі:

`src/data/services.js`

Це дозволяє відокремити дані предметної області від коду компонентів.

Для роботи із заявками використовується спільна локальна колекція, доступна через `RequestsContext`. Для доступу до неї в компонентах застосовується власний хук `useRequests`.

Основними полями заявки є:

- `id` — ідентифікатор заявки;
- `serviceId` — ідентифікатор послуги;
- `customerName` — ім’я замовника;
- `phone` — номер телефону;
- `description` — опис робіт;
- `area` — площа робіт;
- `needsSurvey` — ознака потреби в замірах.

Для роботи з колекцією передбачено операції створення, оновлення та видалення заявок. Колекція зберігається в стані застосунку, тому без додаткового постійного сховища її вміст може скидатися після перезавантаження сторінки.

## 6. Маршрутизація

Для маршрутизації використовується React Router.

Основні маршрути:

- `/` — головна сторінка;
- `/services` — список послуг;
- `/services/:serviceId` — деталі окремої послуги;
- `/requests` — список заявок;
- `/requests/new` — створення нової заявки;
- `/requests/:requestId` — перегляд деталей заявки;
- `/requests/:requestId/edit` — редагування заявки;
- `*` — невідомий маршрут.

Для розділу заявок використовується вкладена маршрутизація. Компонент `RequestsLayout` містить `Outlet`, через який відображаються дочірні сторінки.

## 7. Навігація

Для переходів між сторінками використовуються засоби React Router:

- `Link` — для переходів між сторінками;
- `NavLink` — для основної та вкладеної навігації;
- `useParams` — для отримання параметрів маршруту;
- `useSearchParams` — для читання та зміни параметрів пошуку в URL;
- `useNavigate` — для програмної навігації.

Пошук послуг використовує параметр URL, наприклад:

`/services?search=ремонт`

На сторінці заявок використовуються параметри `q`, `survey` та `sort`. Наприклад:

`/requests?q=Іван&survey=yes&sort=area-asc`

Параметр `q` містить пошуковий текст, `survey` визначає фільтр за потребою в замірах, а `sort` задає спосіб сортування.

Такий підхід дозволяє зберігати вибрані умови в адресі сторінки.

## 8. Керування станом

У застосунку використовуються локальний стан React, власні хуки та Context API.

### Локальний стан

Для даних, які використовуються в межах окремого сценарію, застосовується `useState`.

Зокрема, локальний стан може використовуватися для значень форми, повідомлень про результат операції та інших даних, необхідних для роботи конкретної сторінки.

### Власні хуки

Для доступу до колекції заявок використовується `useRequests`. Він надає компонентам доступ до заявок та операцій над ними.

Для пошуку послуг також використовується власний хук `useServiceFilter`, який формує список `visibleServices` на основі тексту пошуку.

### Context API

Для роботи із заявками використовується `RequestsContext`. Він дає змогу різним сторінкам отримувати доступ до спільної колекції без необхідності передавати її через декілька рівнів `props`.

Для вибору послуги використовується `SelectedServiceContext`, а провайдер `SelectedServiceProvider` розміщено в `AppLayout`.

Споживачами контексту вибраної послуги є компоненти, яким необхідно отримувати або відображати поточний вибір.

### Параметри URL

Пошук, фільтрація та сортування заявок реалізовані через параметри URL за допомогою `useSearchParams`. Це дає змогу узгоджувати стан елементів керування з адресою сторінки.

## 9. Валідація та опрацювання заявок

Під час створення та редагування заявок перевіряється правильність введених даних.

Основні правила перевірки:

- ім’я замовника має бути заповнене та відповідати встановленим обмеженням довжини;
- номер телефону має відповідати очікуваному формату;
- опис робіт має містити достатньо інформації та не перевищувати встановлену довжину;
- площа повинна бути цілим числом у допустимому діапазоні;
- якщо площа перевищує 100 м², необхідно вказати потребу в замірах.

Якщо перевірка не пройдена, користувач отримує повідомлення про помилки та може виправити введені значення.

Для опрацювання заявок передбачено створення, перегляд, редагування та видалення. Перед видаленням виконується підтвердження дії.

## 10. Використання React Bootstrap

Для оформлення окремих елементів інтерфейсу використовується бібліотека React Bootstrap.

Зокрема, компонент `Card` застосовується для відображення окремої послуги в `ServiceCard`. Бібліотека використовується разом із власними CSS-стилями проєкту.

## 11. Повторне використання компонентів

Компонент `Section` використовується для оформлення секцій сторінок.

`ServiceList` відповідає за відображення списку послуг, а `ServiceCard` — за подання окремої послуги.

`AppLayout` та `RequestsLayout` використовуються як спільні оболонки для відповідних маршрутів.

Спільний контекст заявок і власний хук `useRequests` дають змогу повторно використовувати логіку роботи з даними на сторінках створення, перегляду, редагування та списку заявок.

Такий поділ спрощує підтримку коду та подальше розширення функціональності вебзастосунку.
